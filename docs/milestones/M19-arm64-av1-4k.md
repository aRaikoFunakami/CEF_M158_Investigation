# M19: AV1 4K(2160p60)での RAM と、1080p との比較(arm64)

作成: 2026-11-13 17:40 JST(2026-11-13 のユーザー指示「4K AV1 でも同じ情報を取って比較する」)。
ログ: logs/449〜454。結果 JSON: `a64/fp/results/av14k-*-ytmem.json`、`av14klimit-*-ytmem.json`。

前提(M14〜M18 と同じ): S/W デコード(dav1d)+ SwiftShader / ソフトウェア合成の環境。ウィンドウは 1920x1080 のままで、4K の映像は縮小表示される。H/W デコードの実機より RAM は多めに出る。構成間の差は有効。

## 方法

- 動画: YouTube aqz-KE-bpKQ。`ytmem.py --codec av1 --quality hd2160`。実際に **`av01.0.13M.08`(itag 401)3840x2160@60 + Opus** で再生された。
- 条件は M18(H.264 1080p)と同じ 4 つ: G0(ROM 削減なし)/ G2-tv(ROM 最小、SwiftShader なし)× 引数なし / 3 フラグ(`--single-process --no-zygote --enable-low-end-device-mode`)。8 CPU / 8G、warm プロファイル、再生 120 秒、有効 2 回ずつ。

### 4K で AV1 を選ばせる方法(logs/449〜452)

| 方法 | 選ばれたもの |
|---|---|
| 何も上書きせずに hd2160 を要求 | **VP9**(`vp09.00.51.08`、itag 315)3840x2160@60 |
| VP9 / HEVC を「非対応」と答える | H.264 1080p(選べる画質が hd1080 までになる) |
| 「常に AV1 を優先」(`yt-player-av1-pref = 8192`)を入れる | VP9 のまま |
| `mediaCapabilities.decodingInfo` の av01 の問い合わせにだけ powerEfficient = true と答える + 上の設定 | **AV1**(itag 401)3840x2160@60 |

- YouTube は 1080p を超える AV1 を、「AV1 が省電力(= H/W デコードがある)」と答える端末にだけ出している。S/W デコードしかない端末には 4K は VP9 で出す。
- つまり **この計測は「H/W デコーダがあるふりをして、実際は S/W でデコードする」状態**。実機で AV1 の 4K が流れるのは H/W デコーダがある場合で、そのときデコード済みフレームはドライバ側に載る。

| G0 | なし | 1,509.5 | 1,252.6 / 1,303.3 | 1,481.9 | 約 530 | 0〜1 / 7,400 | 2 / 2 |

| G2-tv | なし | 1,131.9 | 974.0 / 1,027.0 | 1,203.7 | 約 540 | 1〜3 / 7,400 | 2 / 2 |

単位 MiB。`media` は memory-infra のダンプでの値(デコード済みフレーム、MSE のバッファなど)。最大は 10 秒おきの標本での値。

- 4K60 の AV1 を S/W でデコードしても、8 CPU ではコマ落ちはほぼ 0 だった。
- 8 試行すべて有効(YouTube の "Something went wrong" は 0 回)。

## 結果 2: 1080p との比較(再生中 PSS)

| 構成 | AV1 1080p60 | H.264 1080p60(M18) | **AV1 4K60** | 4K − H.264 1080p |
|---|---|---|---|---|
| G0、引数なし | 1,060.7(M14) | 1,045.5 | **1,509.5** | +464 |
| G0、3 フラグ | 943.3(M17、1 回) | 912.2 | **1,348.7** | +437 |
| G2-tv、引数なし | 931.8(M14、高い側) | 759.3 | **1,131.9** | +373 |
| G2-tv、3 フラグ | 665.2(logs/440、1 回) | 684.4 | **1,005.5** | +321 |

- **4K にすると +320〜460MiB**。主因は `media` で、1080p の約 134MiB → 4K の約 410〜540MiB(+280〜400MiB)。画素数 4 倍にほぼ比例している。
- **3 フラグの効果は 4K で −126〜−161MiB**(1080p では −75〜−133MiB)。低メモリ端末モードで MSE のバッファが 134 → 21 秒に減り、`media` が約 120MiB 減る。4K ではビットレートが高いので、バッファ秒数を減らす効果が大きい。
- **ROM 削減(G0 → G2-tv)の効果は −378MiB(引数なし)、−343MiB(3 フラグ)**。1080p(−286、−228MiB)より大きく出た。G0 は GPU プロセスが 393MiB(1080p では 290MiB)と大きく、SwiftShader 経由で 4K のフレームを扱う分が加わっている。G2-tv は GPU プロセス 90MiB。
- 最小は G2-tv + 3 フラグの PSS 1,005.5MiB。G0 の引数なしから −504MiB(−33%)。

## 結果 3: 上限つきの確認(logs/454、3 フラグ)

| 構成 | 上限 | 結果 |
|---|---|---|
| G0 | 1,320MiB(回収不可の最大 + 約 200MB) | **再生できた**(OOM 0、上限にも達せず。使用量 1,249〜1,289MiB)。1 回目は YouTube 側の失敗で、2 回目が有効 |
| G2-tv | 980MiB(同 + 約 100MB) | **再生できた**(OOM 0。上限に 2,283 回達し、ファイル由来のページを追い出して収まった。使用量 952〜980MiB で余裕なし) |
| G2-tv | 1,080MiB(同 + 約 200MB) | **再生できた**(OOM 0、上限にも達せず。使用量 991〜1,048MiB) |

## 分かったこと

1. **4K は 1080p より +320〜460MiB 必要**(S/W デコード)。増える分のほとんどはデコード済みフレームと MSE のバッファ。H/W デコードの実機ではフレームがドライバ側に載るので、ブラウザ側の増え方はもっと小さいはず(未計測)。
2. **ROM 最小 + 3 フラグ(G2-tv)なら、AV1 4K60 を約 1GB(980MiB)の上限で再生できる**。削減なし(G0)は 1,320MiB で再生できた(それより下は未確認)。H.264 1080p では G2-tv 640MiB、G0 880MiB だった(M18)。
3. **ROM 削減と 3 フラグの効果は 4K でも有効で、絶対量はむしろ大きい**。
4. 上限の目安は M18 と同じで、「回収不可の最大 + 約 100MB」は余裕なしで通ることがあり、「+ 約 200MB」なら余裕がある。

## 計測上の注意

- 上限つきの有効回数は各 1 回。境界は刻んでいない(G0 の 1,320MiB 未満、G2-tv の 980MiB 未満は未確認)。
- AV1 1080p の 3 フラグの値(943.3、665.2)は各 1 回で、条件も少し違う(上限つき、4 CPU)。4K との比較は H.264 1080p(M18、同条件で有効 2 回)を基準にした。H.264 と AV1 の 1080p の RAM はほぼ同じ(M18)。
- `libcef.so` などのページキャッシュの一部は cgroup の外に課金される(M17 と同じ)。
- 4K で既定の VP9 は計測していない(logs/450 で 40 秒再生し、コマ落ち 0 / 2,423 であることだけ確認)。
