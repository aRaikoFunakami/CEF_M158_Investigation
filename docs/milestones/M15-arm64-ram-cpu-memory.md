# M15: 再生中 RAM は CPU 数・総メモリ・空きメモリに依存するか(arm64)、Cobalt の実行時フラグ

作成: 2026-11-13 12:20 JST。ログ: logs/405〜409(ソース調査)、423(中断)、424(cpu*、cobalt)、429(メモリ量、空きメモリ)、434(二峰性の仮説の確認)。
計測方法は M14 と同じ(G2、YouTube AV1 1080p60、warm プロファイル、再生 60〜120 秒の中央値、3 回の中央値、二峰性の「低い側」の値。単位 MiB)。動画デコードはソフトウェア(dav1d、M14b)。

> **前提の注意(2026-11-13 追記、ユーザーの指摘による)**: この計測の動画デコードはすべてソフトウェア(AV1 を dav1d で CPU デコード、M14b)で、描画も SwiftShader(CPU)である。Cobalt は TV の H/W デコーダを前提にしており、ローエンド機でも AV1 を S/W でデコードすることは想定していない。そのため、**コマ落ちの数字(2 CPU で 15%、Cobalt のフラグ一式で 17〜19%)は実機の前提と違う環境での参考値**で、実機の性能を表さない。RAM の絶対値もレンダラの `media`(dav1d のフレーム、約 140MiB)や CPU 数に応じたデコードスレッドの分だけ多めに出ている。一方、ROM 削減前後の差、低メモリ端末モードの効果、総メモリ・空きメモリに依存しないこと、は同じ条件どうしの差なので有効。8 CPU / 8GB は、比較の基準点、TV に近い条件、ビルドコンテナとコアを重ねないため、という理由でホスト(32 コア / 256GB)から意図して絞った条件。

## 結論

| 要因 | 再生中 PSS への影響 | 理由(ソース) |
|---|---|---|
| CPU 数(2 → 16) | **+39MiB**(898 → 937)。小さい | スレッド数が CPU 数で決まり、スレッドごとのスタックとアロケータのキャッシュの分だけ増える。メモリの大半(動画バッファ、JS ヒープ、本体)は CPU 数に依存しない |
| 総メモリ(1.9G → 16G) | **ほぼなし**(897〜955 の範囲でばらつき程度)。ただし **2,048MB 以下では低メモリ端末モードが自動で ON** | 物理メモリは起動時に読み、V8 のヒープ上限、キャッシュの上限などの「上限」を決めるだけ。動画再生ではどの上限にも届かない |
| 空きメモリ(8G 中 6.5G を他プロセスが使用) | **なし**(923 → 936 / 923) | Linux 版 Chromium は空きメモリを監視しない(メモリ逼迫の評価器が既定で無効)。カーネルが OOM にするまで何もしない |
| 低メモリ端末モード | −24〜−54MiB | M14 参照。MSE のバッファ 170 → 70 秒、GPU 側のキャッシュ |
| Cobalt の実行時フラグ一式 | 低メモリ端末モード単体とほぼ同じ | 効いているのは実質 `--enable-low-end-device-mode` だけ |
| + `--single-process --no-zygote` | **さらに −34MiB**(891.5 → 857.5) | プロセスを分けるための固定費(プロセスごとの本体の私有ページ、各プロセスのヒープの最低量)がなくなる |

**M11 の仮説 5 つの答え合わせ**

1. 「削減前後の差は起動時の差と同程度」→ **ほぼ当たり**。再生前の差 −87、再生中の差 −153MiB(M14)。再生中のほうが差が大きいのは、動画再生で動く GPU プロセスとレンダラの本体のページ(ファイル由来)も増えるため。
2. 「低メモリ端末モードで大きく減る」→ **外れ**。減るのは 24〜54MiB。MSE のバッファ上限は下がるが、この動画では上限まで使っていなかった。
3. 「総メモリで変わる」→ **2GB 以下で自動 ON になる点だけ当たり**。それ以外は変わらない。
4. 「空きメモリでは変わらない」→ **当たり**。
5. 「CPU 数で増える」→ **当たり、ただし小さい**(2 → 16 CPU で +39MiB)。

## CPU 数(logs/424、G2、8G、OFF)

コンテナの `-c N` では `nproc` が N+1 と出た(Apple の container での観測。理由は未確認。表は nproc で記録する)。

| `-c` | nproc | 再生前 | 再生中 PSS | レンダラ | GPU | malloc(レンダラ) | スレッド数(レンダラ / GPU / ブラウザ) | コマ落ち |
|---|---|---|---|---|---|---|---|---|
| 2 | 3 | 299.4 | **897.6** | 483.3 | 223.1 | 123.2 | — | **15.3%** |
| 4 | 5 | 277.9 | **912.4** | 492.3 | 230.2 | 131.2 | 51 / 19 / 35 | 0.6% |
| 8 | 9 | 276.8 | **919.2** | 498.4 | 233.2 | 133.6 | 65 / 22 / 34 | 0.4% |
| 16 | 17 | 277.3 | **936.8** | 522.3 | 229.4 | 139.5 | 84 / 29 / 34 | 0.3% |

- レンダラのスレッドは nproc 5 → 17 で 51 → 84 本。内訳は、ワーカースレッド(max(3, N−1)、V8 のワーカーも同数)、ラスタスレッド(N/2)、dav1d のフレーム / タイルスレッド(min(希望数, N))。
- 1 スレッドあたりの RAM は、使ったスタック(数十〜数百 KB)と、malloc / PartitionAlloc のスレッドごとのキャッシュ。memory-infra でもレンダラの `malloc` が 123 → 140MiB と増えている。
- 2 CPU で 15% のコマ落ち: AV1 1080p60 のソフトウェアデコードと SwiftShader での合成が 2 コアでは追いつかない。**実機の前提(H/W デコード)と違う環境での参考値**で、H/W デコードの実機では起きないはず。
- 2 CPU で ON にした場合: 863.5(低い側 860.0)。

## 総メモリ(logs/429、G2、8 CPU)

| `-m` | MemTotal | モード | 再生中 PSS | MSE のバッファ | JS ヒープ上限 | `deviceMemory` |
|---|---|---|---|---|---|---|
| 1900M | 1,959 | **自動で ON** | **909.2** | 70.1 秒 | 983 | 2 |
| 1900M | 1,959 | `--disable-low-end-device-mode` | 922.3 | 170.6 秒 | 1,028 | 2 |
| 2G | 2,102 | OFF(閾値の 2,048MB を超える) | 916.1 | 170.6 秒 | 1,147 | 2 |
| 3G | 3,047 | OFF | 897.5 | 170.6 秒 | 1,620 | 2 |
| 4G | 4,047 | OFF | 904.1 | 170.6 秒 | 2,120 | 4 |
| 8G | 8,071 | OFF | 919.2 | 170.6 秒 | 4,132 | 8 |
| 16G | 16,107 | OFF | 954.8(有効 2 回、低い側 1 回) | 170.6 秒 | 4,192 | 16 |
| 8G | 8,071 | フラグで ON | 865.7 | 70.5 秒 | **259** | 2 |

- **自動判定は MemTotal ≤ 2,048MB**。`-m 2G` のコンテナは MemTotal 2,101MiB で判定にかからなかった(logs/423)。実機の 2GB 機は、カーネルの予約分を引いた MemTotal が 2,048MB を下回るので自動で ON になるはず。
- 自動 ON とフラグ ON の違い: フラグでは物理メモリが 512MB に見せかけられる(JS ヒープ上限 259MiB)。自動では実際の物理メモリが使われる(983MiB)。MSE のバッファ上限など低メモリ端末としての設定は同じ。
- JS ヒープの上限は物理メモリの約半分(上限 4GB)で変わるが、YouTube の JS ヒープの使用量は 80〜90MiB で、上限にはまったく届かない。
- 4GB を境に画像デコードキャッシュと Skia のキャッシュの上限が 2 倍になるが、動画ページでは使用量が小さく差は出ない(3G 897.5 / 4G 904.1)。
- 16G は YouTube の再生失敗が多く(9 回中 7 回)、有効 2 回(1 回は高い側)なので参考値。

## 空きメモリ(logs/429、G2、8 CPU、8G)

`memhog.py` が計測用 cgroup の外で匿名メモリを確保して常駐した状態(総メモリは 8G のまま)。

| 常駐させた量 | 計測前の available | 再生中 PSS | MSE のバッファ |
|---|---|---|---|
| なし | 7.8GB | 919.2 | 170.6 秒 |
| 5,000MiB | 約 2.8GB | 935.9 | 170.6 秒 |
| 6,500MiB | **約 1.3GB** | 922.9 | 170.6 秒 |

- 空きメモリが 1.3GB まで減っても、Chromium の振る舞い(バッファ量、キャッシュ)は変わらない。
- ソースの裏付け(logs/409): Linux では `SystemMemoryPressureEvaluator::CreateDefaultSystemEvaluator` が nullptr を返す。chrome 層の `DbusMemoryPressureEvaluatorLinux`(systemd の low-memory-monitor を見る)は `kLinuxLowMemoryMonitor`(既定で無効)の裏にある。つまり**メモリが逼迫しても Chromium 側は何も手放さず、足りなくなればカーネルの OOM killer が働く**。Cobalt は独自の評価器(RAM 量に応じて 160 / 300 / 500MiB の予算)でこれを補っている。TV で他のアプリ(放送スタックなど)と RAM を分け合うなら、同様の仕組みか `kLinuxLowMemoryMonitor` の有効化が要る。

## Cobalt の実行時フラグ(logs/424、G2、8 CPU、8G)

Starboard 版 Cobalt の既定フラグのうち、この環境で意味のあるもの(GPU 経路を壊す `--disable-features=Vulkan` は除く):
`--enable-low-end-device-mode --disable-rgba-4444-textures --disable-in-process-stack-traces --disable-accelerated-video-decode --disable-accelerated-video-encode --force-dark-mode --hide-scrollbars --enable-features=SmallerInterestArea,ReclaimPrepaintTilesWhenIdle,ReclaimOldPrepaintTiles,WebAudioRemoveAudioDestinationResampler,DomStorageSmartFlushing --gpu-rasterization-msaa-sample-count=4 --enable-blink-features=PreciseMemoryInfo --js-flags="--no-decommit-pooled-pages --no-concurrent-marking"`

| | 再生前 | 再生中 PSS | プロセス数 | コマ落ち |
|---|---|---|---|---|
| OFF | 276.8 | 919.2 | 9〜10 | 0.4% |
| `--enable-low-end-device-mode` のみ | 272.4 | 865.7(低い側 1 回) | 9〜10 | 0.4% |
| Cobalt のフラグ一式 | 272.3 | 891.5 | 9〜10 | **18.8%** |
| 一式 + `--single-process --no-zygote` | 245.7 | **857.5** | 1 | 17.3% |

- フラグ一式の効果は、低メモリ端末モード単体と区別がつかない(差は 3 回のばらつきの範囲)。タイルの間引き(`SmallerInterestArea` など)はスクロールのあるページ向けで、全画面の動画では効かない。
- **`--single-process` は −34MiB**。全部が 1 プロセス(73 スレッド)になり、プロセスごとの固定費がなくなる。ただし、レンダラが落ちるとブラウザごと落ちる、サンドボックスがなくなる、という代償がある。Cobalt はアプリが 1 つ(YouTube)なのでこれを受け入れている。
- フラグ一式でコマ落ちが 17〜19% に増えた(S/W デコード + SwiftShader の上での現象で、実機の性能を表さない参考値)。候補は `--gpu-rasterization-msaa-sample-count=4`(SwiftShader で 4 倍の MSAA を CPU 処理する)だが、切り分けていない。

## 二峰性の追加調査(logs/434)

「WebGL が使えないと高い側になる」という仮説を、G2 + `--disable-webgl`(4 CPU、4 回)で確かめた。結果は低い側 2 回(916.0)、高い側 2 回(1,111.5)で、**仮説は否定**。WebGL の有無では決まらない。G2-tv が毎回高い側になる理由は分かっていない(ソフトウェア合成の経路で YouTube 側の何かが変わる可能性)。
