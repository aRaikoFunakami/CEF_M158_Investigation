# M18: H.264 1080p での RAM と、上限つきでの再生確認(arm64)

作成: 2026-11-13 16:20 JST(2026-11-13 のユーザー指示「H.264 で 1080p を試したい」)。
ログ: logs/444〜448(準備として logs/439〜443 の single-process の修正)。結果 JSON: `a64/fp/results/h264main-*-ytmem.json`、`h264limit*-ytmem.json`。

前提(M14〜M17 と同じ): S/W デコード(FFmpegVideoDecoder)+ SwiftShader / ソフトウェア合成の環境。H/W デコードの実機より RAM は多めに出る。構成間の差は有効。

## 方法

- 動画: YouTube aqz-KE-bpKQ。`ytmem.py --codec h264 --quality hd1080` で AV1 / VP9 / HEVC を「非対応」と答えさせ、H.264 を選ばせる。実際に **`avc1.64002A`(itag 299)1920x1080@60 + Opus** で再生された。
- 4 条件: G0(ROM 削減なし)/ G2-tv(ROM 最小、SwiftShader なし)× 引数なし / 3 フラグ(`--single-process --no-zygote --enable-low-end-device-mode`)。8 CPU / 8G、warm プロファイル、再生 120 秒、有効 2 回ずつ。
- 方針: Chromium は cgroup の上限に反応しない(M17)ので、上限を細かく刻むのはやめ、制限なしで使用量を測ってから、上限つきは確認だけにした。

- **ROM 削減(G0 → G2-tv)で −286MiB(引数なし)、−228MiB(3 フラグ)**。
- **3 フラグで −133MiB(G0)、−75MiB(G2-tv)**。MSE のバッファが 160 → 60〜70 秒、JS ヒープ上限が 4,132 → 273MiB になる。

## 結果 2: AV1 との比較

| 構成 | AV1 1080p60(再生中 PSS) | H.264 1080p60(再生中 PSS) |
|---|---|---|
| G0、引数なし | 1,060.7(M14) | 1,045.5 |
| G0、3 フラグ | 943.3(M17、800MB 上限つき、1 回) | 912.2 |
| G2-tv、引数なし | 931.8(M14、3 回とも「高い側」) | 759.3 |
| G2-tv、3 フラグ | 665.2(logs/440、4 CPU、1 回) | 684.4 |

- **コーデックを H.264 に変えても RAM はほとんど変わらない**(G0 で −15MiB、G2-tv の 3 フラグで +19MiB。回ごとのぶれの範囲)。レンダラの `media`(デコード済みフレームなど)は H.264 でも約 134MiB(AV1 で約 140MiB)。S/W デコードでは、1080p のフレームを保持する量はコーデックによらない。
- G2-tv の引数なしだけ −172MiB と大きいが、AV1 のときは 3 回とも二峰性の「高い側」(M14)だった。H.264 の回はレンダラの V8 ヒープが約 88MiB で「低い側」に当たる。コーデックの差ではなく二峰性の差と見ている(未確認)。

## 結果 3: 上限つきの確認(logs/447、448、3 フラグ)

| 構成 | 上限 | 結果 |
|---|---|---|
| G0 | 780MiB(回収不可の最大 + 約 100MB) | **2 / 2 回とも YouTube の読み込み中に OOM kill** |
| G0 | 880MiB(同 + 約 200MB) | **再生できた**(OOM 0、上限にも達せず。cgroup 使用量 798〜822MiB) |
| G2-tv | 640MiB(同 + 約 100MB) | **再生できた**(OOM 0。上限には 895 回達し、カーネルがファイル由来のページを追い出して収まった。cgroup 使用量 597〜619MiB) |

- logs/447 の G2-tv・640MiB は、120 秒再生できた後、最後の memory-infra のダンプで OOM kill された(2 / 2)。ダンプ自体がメモリを使うためで、計測側の都合。`ytmem.py` を `--limit` のときはダンプを取らないように直し、logs/448 でやり直した。

## 分かったこと

1. **H.264 にしても RAM は減らない**(S/W デコードの場合)。減らすには解像度を下げるか、H/W デコードでフレームをドライバ側に持たせる必要がある。
2. **必要な上限は「回収不可」だけでは決まらない**。上限に課金されるのは、回収不可(anon + shmem)+ 追い出しきれないファイル由来のページ(実測で約 100〜130MiB)+ カーネル分(約 10MiB)+ 読み込み時の一時的な山。目安は「制限なしの回収不可の最大 + 約 100MB では足りないことがあり、+ 約 200MB なら足りた」。制限なしの計測だけでは決めきれず、上限つきの確認は少数でも必要だった。
3. **ROM 最小 + 3 フラグ(G2-tv)なら 640MiB の上限で H.264 1080p60 を再生できる**。削減なし(G0)は 780MiB で落ち、880MiB で再生できた。**ROM 削減で、必要な上限が約 150〜240MiB 下がる**。
4. M17 の AV1 の結果(G0 は 700MB で OOM、800MB で 1 / 2)と合う。コーデックで必要量は変わらない。

## 計測上の注意

- 上限つきの有効回数は各 1 回。境界(G0 の 780〜880MiB、G2-tv の 640MiB 未満)は刻んでいない。
- `libcef.so` などのページキャッシュの一部は warm プロファイル作成時に cgroup の外で読み込まれ、外側に課金される(M17 と同じ)。実機ではその分も必要になる。
- cgroup の `memory.peak` は使えなかった。リセットが効かず、前の条件の最大値(1,161.7MiB)が残り続けた。使用量の最大は 10 秒おきの標本から取っている。
- 試運転(logs/444)では H.264 の指定が効かず AV1 のままだった。CDP の `Page.addScriptToEvaluateOnNewDocument` は、先に `Page.enable` を呼ばないと注入されない(logs/446)。中断された logs/438(720p の試運転)も同じ状態だったはず。
