# M14: arm64 の YouTube 再生中 RAM — ROM 削減前後 × 低メモリ端末モード

作成: 2026-11-13 09:40 JST。ログ: logs/416〜419、423、426〜428、424(main8c8G)。結果 JSON: `a64/fp/results/main8c8G-<ビルド>-<off|on>-ytmem.json`。

> **前提の注意(2026-11-13 追記、ユーザーの指摘による)**: この計測の動画デコードはすべてソフトウェア(AV1 を dav1d で CPU デコード、M14b)で、描画も SwiftShader(CPU)である。Cobalt は TV の H/W デコーダを前提にしており、ローエンド機でも AV1 を S/W でデコードすることは想定していない。そのため、**コマ落ちの数字(2 CPU で 15%、Cobalt のフラグ一式で 17〜19%)は実機の前提と違う環境での参考値**で、実機の性能を表さない。RAM の絶対値もレンダラの `media`(dav1d のフレーム、約 140MiB)や CPU 数に応じたデコードスレッドの分だけ多めに出ている。一方、ROM 削減前後の差、低メモリ端末モードの効果、総メモリ・空きメモリに依存しないこと、は同じ条件どうしの差なので有効。8 CPU / 8GB は、比較の基準点、TV に近い条件、ビルドコンテナとコアを重ねないため、という理由でホスト(32 コア / 256GB)から意図して絞った条件。

## 計測方法(`tools/fp/ytmem.py`)

- 実行環境: Apple M3 Ultra 上の arm64 ネイティブのコンテナ(Rosetta を通らない)。8 CPU(`nproc` は 9 と出る)、メモリ 8G(MemTotal 8,071MiB)。ビルドは止めた状態。
- 動画: https://www.youtube.com/watch?v=aqz-KE-bpKQ(Big Buck Bunny 60fps)。1080p を要求し、実際に AV1(`av01.0.09M.08`、itag 399)1920x1080@60 + Opus で再生された。デコードはソフトウェア(dav1d)。描画は ANGLE → Vulkan → SwiftShader(G2-tv だけはソフトウェア合成)。
- 手順: ブラウザを専用 cgroup に入れて起動 → 15 秒後に「再生前」を計測 → YouTube を開いて再生 → 再生開始から 120 秒間、10 秒ごとに全プロセスの PSS(anon / file / shmem)、プロセス種別ごとの PSS、cgroup の anon + shmem(回収不可)、プレーヤの統計(コーデック、解像度、バッファ)を記録 → 最後に memory-infra のダンプ(アロケータ別の内訳)。
- 値: 再生開始 60 秒以降の標本の中央値を 1 回の値とし、有効 3 回の中央値。単位 MiB。
- **warm プロファイル**: YouTube を 1 回開いたプロファイルからキャッシュ類を除いて保存し、毎回それをコピーして起動する。新しいプロファイルで毎回開くと、再生位置 40 秒前後で「Something went wrong」になる回が約半数あり(logs/423)、さらに PSS が 200MiB 近く大きい状態になりやすかった(logs/427)。TV でも毎回まっさらなプロファイルで起動することはないので、こちらを標準にした。
- 構成: G0(CEF 既定、ROM 削減なし)、G1(第 2 期の削減を全部適用)、G2(G1 + Cobalt の ROM 項目)、G2-tv(G2 の配布物から SwiftShader を外したもの。ソフトウェア合成)。
- 低メモリ端末モード: `--enable-low-end-device-mode`(ON)/ なし(OFF)。

### ROM 削減前後(G0 → G1、OFF)

- **再生中 PSS は 1,060.7 → 907.4MiB(−153MiB、−14.5%)**。再生前も 362.8 → 276.0MiB(−87MiB)。
- 内訳: ファイル由来 −75MiB(`libcef.so` が 275 → 187MB と小さくなり、各プロセスが読み込むコードとデータが減る)、anon −83MiB。プロセス別ではブラウザ −38、GPU −42、レンダラ −35MiB。
- anon が減るのは、削った機能(拡張機能、PDF、WebUI、各種サービス)が起動時に作っていたオブジェクトがなくなることと、再配置で書き換わる `.data.rel.ro` などのページ(プロセスごとの私有ページで anon に数えられる)が小さくなる(データ 14.0 → 11.3MB)ため。
- G1 → G2(Cobalt の ROM 項目)は誤差の範囲(ROM の差も 0.5MB)。

### 低メモリ端末モード(OFF → ON)

- **効果は −24〜−53MiB**(G0 −52、G1 −24、G2 低い側どうしで −54)。思ったより小さい。
- 確実に効いているもの:
  - **MSE のバッファ**: 170 秒分 → 70 秒分。YouTube は再生済みの部分も消さずに持つので、OFF では 120 秒再生した時点で全区間(約 170 秒)がメモリにある。ON では上限が動画 150MB → 30MB になり、Chromium の MSE が古い区間から捨てる。ただしこの動画(AV1 1080p。30MB で約 70 秒なので約 3.5Mbps)は 170 秒でも約 75MB なので、差は約 45MB にとどまる。高ビットレート(4K、VP9 の高画質)ほど効く。memory-infra では差がレンダラの `malloc`(−10MiB)と `media`(−7MiB)に現れる。
  - **GPU プロセス −28〜−37MiB**: GPU 側のキャッシュ(シェーダのプログラムキャッシュ 6MB → 128KB、転送用バッファ)が絞られる。
  - **JS ヒープの上限** 4,132 → 259MiB、`navigator.deviceMemory` 8 → 2(物理メモリが 512MB に見せかけられるため)。YouTube はこれを見て挙動を変えうるが、この動画では解像度は 1080p のまま、JS ヒープの使用量も同程度だった。
- 効かなかったもの: 画像デコードキャッシュや Skia のキャッシュは上限が下がるが、動画再生ページでは使用量が小さい(memory-infra の `cc` は 16〜18MiB、うち画像 6〜9MiB)ので差が出ない。

### SwiftShader の有無(G2 → G2-tv)

- G2-tv は描画をソフトウェア合成で行うので、GPU プロセスが 233 → 65MiB に減る代わりに、レンダラが合成とラスタを自分で行い大きくなる。合計はほぼ同じ(低い側どうしでは +13MiB)。
- ただし G2-tv は 3 回とも「高い側」だった(下記)。

## 二峰性(logs/426、427、424)

同じ構成・条件でも、再生中 PSS が約 180MiB 大きい回がある。memory-infra で比べると、高い側はレンダラの V8 ヒープが 105〜121MiB(低い側は 79〜89MiB)で、きれいに 2 つに分かれる。

| 条件 | 低い側の回数 | 高い側の回数 |
|---|---|---|
| 新しいプロファイル(logs/423、427) | ほぼ 0 | ほぼ全部 |
| warm プロファイル、SwiftShader あり(logs/424 の G0、G1、G2) | 15 | 3 |
| warm プロファイル、SwiftShader なし(G2-tv) | 0 | 6 |

- YouTube 側が配る JS や状態の違いと考えている。SwiftShader なし(WebGL なし)だと毎回高い側になることから、「WebGL が使えるかどうかで YouTube の動作が変わり、SwiftShader の初期化が遅れた回に WebGL なしと判断される」という仮説を立てた(`--disable-webgl` で確かめる予定)。
- 比較では、構成ごとに低い側の回の中央値を使う(`tools/fp/ytanalyze.py`)。

## 注意

- cgroup の `memory.peak` は、このカーネルでは書き込みでリセットできず、コンテナ内の過去最大値が残る。ピークは PSS の最大値で見る。
- logs/424 の main8c8G は結果名を off / on だけにしてしまい、ビルドごとに上書きされた。`tools/a64rescue.sh` で更新のたびにビルド名付きで退避した(全 8 件)。スクリーンショットは最後のビルド(G2-tv)の分だけ残っている。
