# M20: 動画再生時の RAM のまとめ(H.264 1080p / AV1 4K × 通常 / メモリ削減 × フラグなし / あり)

作成: 2026-11-13(ユーザー指示: 現在の調査結果だけで、2 種類の動画 × 通常 / メモリ削減 × `--single-process` フラグなし / ありをまとめる。追加の計測はしない)。
元データ: M18(logs/445、447、448)、M19(logs/453、454)。

## 条件

- 環境: arm64 の Linux コンテナ(8 CPU / 8G)、CEF 158(cefsimple)、YouTube の Big Buck Bunny 60fps(aqz-KE-bpKQ)を 120 秒再生、有効 2 回の中央値。
- デコードは S/W(H.264 は FFmpeg、AV1 は dav1d)。H/W デコードの実機より RAM は多めに出る。構成間の差は有効。
- 「通常」= G0(CEF 既定、ROM 削減なし)。「メモリ削減」= G2-tv(ROM 削減を全部適用、SwiftShader なし)。
- 「フラグあり」= `--single-process --no-zygote --enable-low-end-device-mode` の 3 つをまとめて付けた状態。
- PSS = 全プロセスの合計。回収不可 = anon + shmem(カーネルが追い出せない分)。単位 MiB。
- 1080p は H.264(`avc1.64002A`、1920x1080@60)で計測した。H.265(HEVC)は計測していない(ユーザー確認済み: H.264 でよい)。

## 「再生を確認できたメモリ上限」の意味

- ブラウザの全プロセスが入る cgroup に `memory.max`(スワップなし)で上限をかけ、その状態で YouTube を 120 秒再生して、落ちずに再生が進み続けた上限値。
- 上限を超えそうになると、カーネルがまずファイル由来のページを追い出し、それでも足りなければ OOM killer がブラウザを強制終了する。
- PSS と回収不可は「制限なしで使わせたときの使用量」、この列は「実際に制限をかけて試した結果」。上限は回収不可より 100〜200MiB 大きい値が必要だった(追い出しきれないファイル由来のページとカーネル分も数えられるため)。
- **最小値ではない**。試したのは 1〜2 点で、「この値なら再生できた」という確認。それより下でどこまで再生できるかは試していない。
- 「未確認」は上限つきの試験をしていない条件(試したのはフラグありだけ)。
- 端末の搭載 RAM ではなく、ブラウザだけに割り当てる量。実機では OS やほかのプロセスの分が別に要る。

## 読み取れること

1. **ビルドの削減とフラグを両方使うと、どちらの動画でも約 1/3 減る**(1080p で −35%、4K で −33%)。
2. **効果が大きいのはビルドの削減**(−25〜−27%)。フラグだけでは −11〜−13%。
3. **4K は 1080p より +320〜460MiB 多い**。増える分のほとんどはデコード済みフレームと MSE のバッファ(1080p で約 134MiB → 4K で約 410〜540MiB)。
4. **再生できる上限**(フラグあり): 1080p はメモリ削減で 640MiB、通常で 880MiB。4K はメモリ削減で約 1GB、通常で 1,320MiB。

## 断り書き

- S/W デコードの値。H/W デコードの実機ではデコード済みフレームがドライバ側に載るので、ブラウザ側の RAM はこれより小さくなるはず。
- AV1 の 4K は、YouTube に「AV1 が省電力(H/W デコードあり)」と答えさせて選ばせた。何もしなければ 4K は VP9 になる。
- 上限つきの確認は各 1 回で、フラグありの条件だけ。境界は刻んでいない。
- PC 向けの YouTube のページで計測した(TV 向けの `youtube.com/tv` ではない)。
