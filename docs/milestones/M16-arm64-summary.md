# M16: 第 3 期(arm64)の調査結果まとめ

作成: 2026-11-13 12:40 JST。ログ: logs/400〜434。詳細は M11(調査と計画)、M12(ビルド)、M13(Cobalt の ROM 項目)、M14(削減前後 × 低メモリ端末モード)、M14b(S/W か H/W か)、M15(CPU 数・メモリ量の依存、Cobalt の実行時フラグ)。

> **前提の注意(2026-11-13 追記、ユーザーの指摘による)**: この計測の動画デコードはすべてソフトウェア(AV1 を dav1d で CPU デコード、M14b)で、描画も SwiftShader(CPU)である。Cobalt は TV の H/W デコーダを前提にしており、ローエンド機でも AV1 を S/W でデコードすることは想定していない。そのため、**コマ落ちの数字(2 CPU で 15%、Cobalt のフラグ一式で 17〜19%)は実機の前提と違う環境での参考値**で、実機の性能を表さない。RAM の絶対値もレンダラの `media`(dav1d のフレーム、約 140MiB)や CPU 数に応じたデコードスレッドの分だけ多めに出ている。一方、ROM 削減前後の差、低メモリ端末モードの効果、総メモリ・空きメモリに依存しないこと、は同じ条件どうしの差なので有効。8 CPU / 8GB は、比較の基準点、TV に近い条件、ビルドコンテナとコアを重ねないため、という理由でホスト(32 コア / 256GB)から意図して絞った条件。

## 依頼(2026-11-12 23:00)と答え

1. **arm64 で CEF の ROM をどこまで減らせるか** → 配布物 366.3MB → **219.6MB(−40.0%)**、GPU のある実機向けに SwiftShader も外すと **196.0MB(−46.5%)**。本体(strip 後)は 275.1 → 186.7MB(−32.1%)。第 2 期までの削減はソースの修正なしで arm64 に当てられた。
2. **YouTube 再生中の RAM、削減前後** → 再生中 PSS **1,060.7 → 907.4MiB(−153MiB、−14.5%)**、再生前 362.8 → 276.0MiB。
3. **RAM は CPU 数や残りメモリに依存するか** → **ほとんど依存しない**。CPU 2 → 16 で +39MiB(スレッド分)。総メモリ 1.9 → 16GB と空きメモリ 7.8 → 1.3GB では変わらない。ただし総メモリ 2,048MB 以下では低メモリ端末モードが自動で ON になる。Linux 版 Chromium は空きメモリを監視しないので、足りなくなれば OOM killer 任せになる。
4. **`--enable-low-end-device-mode` の ON / OFF** → **−24〜−54MiB**。MSE のバッファが 170 → 70 秒分、GPU 側のキャッシュ、JS ヒープ上限 4,132 → 259MiB。ビットレートの低いこの動画では MSE の上限に届かず、効果は小さかった。
5. **Cobalt のノウハウ** → ROM は 4 引数を追加適用して −0.5MB(第 1・2 期でほぼ取り尽くしていた)。実行時フラグは低メモリ端末モード以外は効果が見えず、`--single-process` だけ −34MiB。
6. (追加の依頼)**動画デコードは S/W か H/W か** → **すべて S/W**(AV1 は dav1d、H.264 は FFmpeg)。実行環境に GPU / 動画エンジンがない。

## 分かったこと(記事の要点)

1. **ROM を減らすと RAM も減る**。再生中で −153MiB。半分はファイル由来(本体が小さいので各プロセスが読み込むページが減る)、半分は anon(削った機能が起動時に作っていたオブジェクトと、再配置で書き換わる私有ページ)。
2. **低メモリ端末モードは「上限」を下げるだけ**で、上限に届いていない資源には効かない。効いたのは MSE のバッファ(YouTube は再生済みの区間も保持するので、長く見るほど効く)と GPU 側のキャッシュ。
3. **Chromium の RAM は環境に「適応」しない**。総メモリは起動時に上限の計算に使うだけ、空きメモリは見ない、CPU 数はスレッド数を通じて少し効くだけ。TV で RAM を他と分け合うなら、Cobalt のように独自のメモリ予算と逼迫時の解放(`MemoryPressureListener`)を入れる必要がある。
4. **x64(Rosetta)の RAM の絶対値は使えない**。起動時の回収不可が実機より約 235MiB 大きく出ていた。第 1・2 期の数値は構成間の差だけが意味を持つ。
5. **arm64 の SwiftShader は重い**(ROM 22.8MB、LLVM 入り)。実験用の部品で、GPU のある実機では外せる。
6. **計測の落とし穴**:
   - YouTube は新しいプロファイルで何度も開くと、再生位置 40 秒前後で「Something went wrong」になる回が約半数ある。さらに PSS が約 200MiB 大きい状態になりやすい。1 回開いたプロファイルを使い回す(warm プロファイル)と安定する。
   - それでも、レンダラの V8 ヒープが 80〜89MiB の回と 105〜121MiB の回に分かれる(二峰性)。原因は特定できていない(WebGL の有無ではない)。比較は V8 ヒープで分けた低い側どうしで行った。
   - ビルドと並行して計ると、CPU の取り合いでコマ落ちが 30〜40% になる。RAM の比較はビルドを止めて行った。
   - arm64 ネイティブでは子プロセスが `setproctitle` で cmdline を書き換えるので、プロセス種別の判定は空白でも区切る。
   - `-m 2G` のコンテナの MemTotal は 2,101MiB で、低メモリ端末の自動判定(2,048MB 以下)にかからない。
7. **今回の数値は S/W デコード**。H/W デコードの実機では、動画フレームがドライバ側に移り、レンダラの `media`(約 140MiB)が減って GPU / カーネル側が増える。CPU 依存(2 CPU でコマ落ち 15%)もほぼ消えるはず。

## 残したこと

- 二峰性の原因(YouTube 側の状態か、Chromium 側か)。
- Cobalt のフラグ一式でコマ落ちが増えた原因(MSAA 4 倍の切り分け)。
- H/W デコードの実機での RAM(この環境では計れない)。
- `angle_enable_vulkan=false` の実測(GL ドライバのある環境が要る)。
