# 起動時の RAM 消費

作成: 2026-11-12。ツール: `tools/fp/startram.py`。生データ: `logs/results/*-startram.json`、`logs/178-m6-startram-all.log`。

## 方法

https://qiita.com/rairaii/items/d5a5c3da56dbc7063a19 の方法に合わせた(UPX 圧縮の比較は対象外)。

- **回収できない RAM** = `anon` + `shmem`。cgroup v2 の `memory.stat` から読む。計測専用の cgroup(`/sys/fs/cgroup/fpmeas`)にブラウザだけを入れる(logs/174)。全プロセスの `smaps_rollup` の `Pss_Anon + Pss_Shmem` 合計とも突き合わせる(差は 1% 以内)。
- **ファイル由来**(`Pss_File`)= 実行ファイルや pak のページキャッシュ。メモリが足りなくなればカーネルが捨てて読み直せる。
- **本体マッピング** = 実行ファイル本体(`chrome` / `content_shell` / `libcef.so`)のマッピングの RSS と PSS を全プロセスで合算(`/proc/*/smaps`)。
- 条件: ローカルページ(`http://127.0.0.1:8000/caps.html`)を 1 枚開いて 30 秒後。3 回の中央値。単位は **MiB**(記事と同じ。他の表の MB = 10^6 バイトとは違う)。
- 起動オプションは動作確認と同じ(`--no-sandbox`、SwiftShader、1920x1080)。

## 読み方

- `chrome` → `content_shell` で回収不可が 800 → 342MiB(−458)。プロセス数が 14 → 9 に減り、`//chrome` 層の初期化で確保するヒープがなくなる。
- CEF(Alloy スタイル)は 9 プロセスで `content_shell` と同じだが、回収不可は 452MiB(E1)。`content_shell` より 110MiB 多い。`//chrome` 層の常駐サービス分。
- バイナリを削っても回収不可はあまり減らない(E1 → E3b で −40MiB、C → D3c で −29MiB)。減るのは主にファイル由来(E1 → E3b で −34MiB、C → D3c で −29MiB)。
- 本体 RSS は「触ったページ」の合計で、プロセス間で共有される。PSS(共有を按分)は RSS の 3 分の 1 前後。

## 注意

- Apple Silicon 上の Rosetta で x64 バイナリを動かしている。翻訳済みコードが匿名ページに載るので、実機より大きく出る可能性がある。構成間の比較に使う。
- 1 ページを開いた直後の値。YouTube 再生中の PSS は `logs/chromium-summary.md` と `logs/cef-milestones/M5-summary.md` を参照。

- 回収不可(anon + shmem)は E3b 412.0 → F4a 404.1MiB。バイナリを 61MB(23%)削っても 8MiB しか減らない。
- ファイル由来(`Pss_File`)は 197.7 → 159.8MiB(−37.9)。うち約 24.5MiB は RELR で再配置テーブル(25.8MB)を読まなくなった分。F1a の時点で 173.2MiB になっている。
- Chromium 編でも同じ傾向: RELR で `Pss_File` が 122.7 → 110.9MiB、回収不可は 296.0 → 296.1MiB で変わらない。
- 配布物だけを削った F4a-dist は、この計測では RAM が変わらない(ICU データを 5.6MB 小さくしても `Pss_File` は 159.8 → 159.6MiB)。
- **拡張機能を外すと回収不可が 40MiB 減る**(F4a 404.1 → F4b 364.0MiB、プロセス数 9 → 8)。内蔵のコンポーネント拡張機能の Service Worker 用レンダラ(PSS 約 45MiB)が常駐しなくなるため(logs/311)。第 2 期で回収不可が目に見えて減ったのはこの 1 件だけ。
